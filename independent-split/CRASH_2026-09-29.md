# SpringBoard crash and black CarPlay panes — 2026-09-29

Device: iPhone10,2, iOS 16.7.16, Dopamine rootless. User supplied
`SpringBoard-2026-09-29-100255.txt` and screenshots of Safe Mode and a black
external split window with only the swap/menu controls visible.

The SpringBoard report records launch at 10:01:53, crash capture at 10:02:27,
`EXC_CRASH/SIGABRT`, two consecutive crashes, and a last exception backtrace
through `-[SBAppViewController dealloc]+192`. `CarPlaySplit.dylib` was injected.
The report does not include the Objective-C exception reason or a tweak frame,
so exact attribution to one caller cannot be proven from the report alone.

Our host called `setRequestedMode:0` (an asynchronous requested transition),
then detached and released the controller in `close`. That is consistent with
the deallocation assertion. The public carplay-cast reference uses
`_setCurrentMode:0` during dismissal. Alpha3 resets the current mode before
releasing the controller and refuses to host on systems lacking that method.

The black panes are separately observed. Our previous controller identifier
was a random `CarPlaySplit.<UUID>`; the reference uses the hosted app's bundle
identifier. Alpha3 uses the bundle identifier and shows a loading state until
the application scene exists, followed by the existing timed error if it never
arrives. This is a hypothesis for the black framebuffer, not proof of rendering.

Verification gate: build and package checks, deployment state and package hash,
then a new physical-device test for both visible applications, pane resizing,
exit and repeated entry. A successful build cannot establish that the black
panes or the SpringBoard crash are solved.
